You are the planning and architecture model for a software project.

Do NOT jump straight into coding.

First investigate the current official documentation, resolve conflicting information, test the most important assumptions where possible, and then produce a detailed implementation plan that a coding agent can execute phase by phase.

The product is an AI-enabled, cloud-hosted trading journal for a professional meme-coin trader using GMGN to trade Robinhood Chain.

The application should automatically ingest objective trade data, while the trader manually records only the subjective decision-making that the API/blockchain cannot know.

The core journal model is NOT a generic "notes" field.

It is a chronological THESIS TIMELINE that changes over the life of a trade.

The system should preserve exactly what the trader believed at each decision point and later use AI + quantitative analysis to determine which types of reasoning, catalysts, setups, behavioral patterns, and trade-management decisions actually produce good results.

The trader uses GMGN normally.

TGCOINS

Buy Thesis (150k):
Good technology by an account that makes memecoins, could send if a big KOL claims their tokens.

# THESIS TIMELINE MODEL

Do NOT create a single mutable `reasoning` or `thesis` field.

A trade should contain immutable timestamped thesis events.

Conceptually:

trade_episode
|
|-- thesis_event: BUY
|   - written_at
|   - market context at writing time
|   - original text
|   - references
|
|-- fill
|-- fill
|
|-- thesis_event: HOLD
|   - written_at
|   - original text
|   - thesis status
|
|-- partial sell
|
|-- thesis_event: HOLD
|
|-- fill
|
|-- thesis_event: SELL
|   - written_at
|   - original text
|   - thesis status
|
|-- general_thoughts

Every thesis event must preserve the ORIGINAL trader-authored text or transcript.

Never overwrite it with an AI-generated summary.

AI may create structured features in separate records.

This is essential so historical reasoning can be reprocessed later with better models.

---

# THESIS EVENT TYPES

At minimum support:

BUY

HOLD

SELL

GENERAL_THOUGHT

OPTIONAL_FILL_NOTE

The difference matters.

BUY THESIS:
Why does the trader believe this asset is mispriced upward at entry?

HOLD THESIS:
Why is continuing to hold still attractive given new information and current price?

SELL THESIS:
Why is reducing or closing the position now better than continuing to hold?

GENERAL THOUGHT:
What did the trader learn about the token, developer, narrative, market structure, or setup that is useful beyond the immediate sell decision?

OPTIONAL FILL NOTE:
Why did the trader make a meaningful add/reduction at a particular moment?

Do NOT force a thesis for every single fill.

---

# THESIS STATUS

When writing HOLD or SELL reasoning, allow an optional extremely low-friction thesis status:

* Stronger
* Unchanged
* Weaker
* Invalidated

The application should make this one-click.

This is useful for evaluating process.

Examples:

good process / losing trade:
thesis invalidated
→ trader exits quickly

bad process:
thesis invalidated
→ trader continues holding or adds

good outcome / weak process:
thesis already weakened
→ price happens to rise anyway

The analysis layer should explicitly distinguish outcome quality from decision quality.

# TRANSACTIONS ARE NOT TRADES

Do not equate one API transaction with one journal trade.

A trade is a POSITION EPISODE.

Example:

BUY $500
BUY $300
BUY $700
SELL $400
SELL $600
SELL remainder

This should generally be one trade episode containing multiple fills.

Initial deterministic model:

position:
0 → >dust threshold
= OPEN EPISODE

position remains >dust
= SAME EPISODE

position:

> dust → <=dust
> = CLOSE EPISODE

later:
0 → >dust
= NEW EPISODE

Support:

* scaling in;
* scaling out;
* multiple buys;
* partial exits;
* full exits;
* re-entry after closing;
* repeated trading of same token;
* transfers;
* airdrops;
* dust;
* eventual multiple wallets.

Create clear edge-case handling.
